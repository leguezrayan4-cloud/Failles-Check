# FaillesCheck — configuration de la synchronisation distante (Supabase)

L'application fonctionne **sans aucune configuration** : catalogue public NVD (NIST),
cache local et données de démonstration (DÉMO · FICTIF).

La synchronisation distante est **facultative**. Elle sert à stocker vos logiciels suivis
et un miroir des vulnérabilités dans une base gratuite.

> ⚠️ Aucune clé n'est écrite dans le projet. Vous devez créer le service vous-même
> et fournir la configuration localement.

---

## 1. Créer le projet distant (gratuit)

1. Créez un compte sur <https://supabase.com> (offre gratuite, aucun moyen de paiement requis).
2. Créez un projet (nom libre, région la plus proche, mot de passe base de données fort).
3. Dans **Project Settings → API**, notez :
   - **Project URL** : `https://<votre-projet>.supabase.co`
   - **anon public key** : la clé publique (elle est *conçue* pour être exposée côté client ;
     ce n'est **pas** la clé `service_role`, qui doit rester secrète).

## 2. Créer les tables

Dans **SQL Editor**, exécutez :

```sql
-- Vulnérabilités (miroir des données publiques NVD, lecture seule côté application)
create table if not exists public.vulnerabilities (
  id text primary key,
  title text,
  severity text,
  score numeric,
  product text,
  affected_version text,
  status text,
  summary text,
  description text,
  remediation text,
  vector text,
  url text,
  source text,
  published text,
  updated_at timestamptz default now()
);

-- Logiciels suivis par chaque installation (identifiés par client_id)
create table if not exists public.software (
  id bigint generated by default as identity primary key,
  client_id text not null,
  local_id text,
  name text not null,
  version text,
  editor text,
  identifier text,
  created_at timestamptz default now(),
  unique (client_id, local_id)
);

alter table public.vulnerabilities enable row level security;
alter table public.software enable row level security;

-- Lecture publique du catalogue de vulnérabilités
create policy "vuln_read_all" on public.vulnerabilities
  for select using (true);

-- Écriture des vulnérabilités : réservée à l'import (tableau de bord / service_role).
-- L'application n'a besoin que de la lecture.

-- Logiciels : autorisés pour la clé anon (petit projet sans authentification).
create policy "software_read" on public.software for select using (true);
create policy "software_insert" on public.software for insert with check (true);
create policy "software_delete" on public.software for delete using (true);
```

> **Limite connue :** sans Supabase Auth, ces règles sont permissives : toute personne
> possédant l'URL et la clé `anon` peut lire/écrire la table `software`.
> Pour un usage sérieux, activez Supabase Auth et remplacez les règles par
> `using (auth.uid() = owner)` sur une colonne `owner uuid`.
> L'application filtre déjà par `client_id`, ce qui cloisonne les installations
> entre elles mais **ne constitue pas** une frontière de sécurité.

## 3. Fournir la configuration à l'application (sans la versionner)

Créez le fichier **hors du projet** :

```
user://faillescheck_remote.json
```

Chemin réel selon la plateforme :

| Plateforme | Emplacement |
|---|---|
| Windows | `%APPDATA%\Godot\app_userdata\Failles Check\faillescheck_remote.json` |
| macOS | `~/Library/Application Support/Godot/app_userdata/Failles Check/faillescheck_remote.json` |
| Android | `/data/data/<package>/files/faillescheck_remote.json` (accès app) |
| iOS | dans le bac à sable de l'app (voir note ci-dessous) |

Contenu :

```json
{
  "url": "https://votre-projet.supabase.co",
  "anon_key": "VOTRE_CLE_ANON_PUBLIQUE",
  "software_table": "software",
  "vuln_table": "vulnerabilities"
}
```

Alternative (utile en développement sur ordinateur) — variables d'environnement,
qui sont prioritaires sur le fichier :

```
FAILLESCHECK_SUPABASE_URL=https://votre-projet.supabase.co
FAILLESCHECK_SUPABASE_ANON_KEY=votre_cle_anon_publique
```

## 4. iOS

Le bac à sable iOS ne permet pas de déposer facilement un fichier dans `user://`.
Deux options :

- **Recommandée** : activer Supabase Auth et injecter la configuration au premier lancement
  via un écran de connexion (à développer) ;
- **Rapide** : exposer l'URL et la clé `anon` comme paramètres du projet Godot
  (`Project Settings → Synchronisation`), en gardant à l'esprit que la clé `anon` est
  alors embarquée dans le binaire — acceptable car publique par conception, mais **jamais**
  pour une clé `service_role`.

## 5. Vérification

Dans l'application : **Paramètres → Compte** affiche
« configurée / non configurée », l'identifiant d'appareil et la date de la dernière synchro.
Le bouton **Synchroniser maintenant** envoie les logiciels locaux et récupère ceux du compte.

## Comptes utilisateurs (Supabase Auth)

L'application utilise **uniquement la clé publique « anon »**. Aucune clé
`service_role` n'est présente dans le projet.

### 1. Activer la connexion par e-mail
Tableau de bord Supabase → **Authentication → Providers → Email** : activer
« Enable Email provider ». Laisser « Confirm email » activé pour exiger la
validation de l'adresse.

### 2. Adresses de redirection
**Authentication → URL Configuration** :
- *Site URL* : `https://votre-domaine` (ou l'URL de votre choix) ;
- *Redirect URLs* : ajouter la même URL. Le lien de validation envoyé par
  e-mail y renvoie l'utilisateur.

### 3. Suppression de compte côté serveur
Créer la fonction SQL suivante (SQL Editor). Elle supprime uniquement le
compte de l'utilisateur authentifié, jamais celui d'un autre :

```sql
create or replace function public.delete_own_account()
returns void
language plpgsql
security definer
set search_path = public
as $$
begin
  delete from auth.users where id = auth.uid();
end;
$$;

revoke all on function public.delete_own_account() from public;
grant execute on function public.delete_own_account() to authenticated;
```

### 4. Règles de sécurité des tables
Les tables `software` et `vulnerabilities` doivent rester protégées par RLS
(voir la section précédente). Chaque utilisateur ne peut lire et modifier que
ses propres lignes (`auth.uid() = user_id`).

### 5. Configuration côté application
Créer `user://faillescheck_remote.json` (dossier de données de l'application) :

```json
{
  "url": "https://VOTRE-PROJET.supabase.co",
  "anon_key": "VOTRE_CLE_PUBLIQUE_ANON"
}
```

Ou définir les variables d'environnement `FAILLESCHECK_SUPABASE_URL` et
`FAILLESCHECK_SUPABASE_ANON_KEY` (prioritaires).

Tant que cette configuration est absente, l'écran **Compte** affiche
« Configuration requise » et aucune requête réseau n'est envoyée.

## Schéma réel du projet (vérifié)

L'application utilise **le JWT de l'utilisateur connecté** pour toutes les
écritures : les règles RLS s'appliquent côté serveur. Seule la clé publique
`sb_publishable_…` est utilisée.

### `profiles`
Colonnes utilisées : `id` (uuid = `auth.users.id`), `display_name`, `created_at`.
L'adresse e-mail reste dans `auth.users` (aucune colonne `email`).

### `user_software`
Colonnes utilisées : `id`, `user_id`, `name`, `version`, `publisher`,
`is_favorite`, `created_at`.

Correspondances côté application :
- éditeur → `publisher`
- favori → `is_favorite`
- identifiant CPE → conservé localement uniquement (pas de colonne distante)

L'application ne suppose **aucune contrainte unique** : elle met à jour la
ligne existante (`PATCH` filtré sur `user_id` + `name`) puis crée la ligne si
aucune n'existe.

### Droits à vérifier côté serveur
Le rôle `anon` n'a aucun droit sur ces deux tables (vérifié : HTTP 401
« permission denied »). L'application n'utilise jamais `anon` pour ces tables,
mais le rôle `authenticated` doit disposer des droits :

```sql
grant select, insert, update, delete on public.profiles to authenticated;
grant select, insert, update, delete on public.user_software to authenticated;
```

Les politiques RLS doivent autoriser l'utilisateur sur ses propres lignes :

```sql
-- profiles
create policy "profiles_select_own" on public.profiles
  for select to authenticated using (auth.uid() = id);
create policy "profiles_insert_own" on public.profiles
  for insert to authenticated with check (auth.uid() = id);
create policy "profiles_update_own" on public.profiles
  for update to authenticated using (auth.uid() = id) with check (auth.uid() = id);

-- user_software
create policy "user_software_select_own" on public.user_software
  for select to authenticated using (auth.uid() = user_id);
create policy "user_software_insert_own" on public.user_software
  for insert to authenticated with check (auth.uid() = user_id);
create policy "user_software_update_own" on public.user_software
  for update to authenticated using (auth.uid() = user_id) with check (auth.uid() = user_id);
create policy "user_software_delete_own" on public.user_software
  for delete to authenticated using (auth.uid() = user_id);
```

### Configuration locale (hors projet)
`user://faillescheck_remote.json` est écrit dans le dossier de données privé de
l'application (jamais dans `res://`, jamais versionné) :

```json
{
  "url": "https://VOTRE-PROJET.supabase.co",
  "anon_key": "sb_publishable_…",
  "profiles_table": "profiles",
  "user_software_table": "user_software",
  "vuln_table": "vulnerabilities"
}
```

Seule une clé **publique** est acceptée : `RemoteConfig.save_config()` refuse
toute clé `service_role` (rôle lu dans le JWT ou préfixe `sb_secret_`). La clé
n'est jamais affichée en entier dans l'interface (`sb_pub…-_P6`).
